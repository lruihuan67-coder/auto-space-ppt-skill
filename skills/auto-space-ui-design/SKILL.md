# 凹凸时空 UI 设计

用这套已实现的设计系统完成两类任务。先读 [设计规范](references/design-rules.md)，再根据用户是否已有前端项目选择模式。用户提供的业务内容、目标设备、主题或参考图优先；未指定时以中文、桌面端 1440px、亮色主题开始。不要虚构真实客户、业绩或业务指标；示例数据应明确标为示例。

## 模式一：从零搭建界面

用户还没有应用或前端页面时，从 `assets/ui-starter/` 复制出独立项目，按需求组合组件，建立需要的页面、导航和基础交互。可用 starter 的后台与组件展示页学习用法，但页面结构应由用户的业务任务决定，不直接交付示例页充数。没有真实后端时，明确标记演示数据和本地交互，不假装接口已接通。默认交付可运行的前端页面与可查看的预览；若用户只要 UI 图，再导出目标尺寸的清晰 PNG。

## 可复用资源

- `assets/ui-starter/` 是可运行的 React + TypeScript + Tailwind 4 项目，内含组件、Token、Logo、后台示例和组件展示页。`/` 是后台示例，`/library` 是组件展示页。源代码均可编辑，复制到本次任务的输出目录使用，不要直接修改 Skill 自身的资产。
- `assets/foundation-reference.png` 只供核对色彩和品牌气质；布局以本次内容和组件规范为准。
- 若用户已有项目，按需移植 `assets/ui-starter/src/components`、`src/lib/utils.ts`、`src/styles.css` 中相关部分及 `public/brand`；沿用其现有结构，不覆盖用户页面。

## 模式二：优化已有前端

用户已有前端项目时，在原项目中按品牌规范优化界面，不重建业务。将原界面视为内容与功能基线：先记录页面文案、数字、表格字段与行、图片、菜单项、表单字段、链接/路由及交互行为，再修改颜色、字体、间距、圆角、图标、容器、组件外观和必要的响应式布局。可以替换组件实现，但须保持相同的信息、顺序、操作入口、数据来源和行为；不要擅自增删模块、改写文案、替换图片或编造示例数据。用户明确要求变更的内容除外。

有源码时，先确认它的框架、样式体系与组件接口，只移植适合的 Token、Logo 和组件；保持其业务逻辑及项目结构。不要把整个页面换成 starter 的后台示例。交付前比较改前/改后的可见文字和数据，运行原项目适用的构建或检查，并实际检查关键交互。如果只提供截图，可以出视觉改版图，但只能核对截图中可见的内容，不能声称已保持原页面的隐藏状态或功能；文字模糊时不要猜测。

## 出图方式

优先用配套 React 组件拼出真实页面，再在目标尺寸的浏览器中截取 PNG；这样设计图与前端可用组件保持一致。若用户指定 Pencil、Figma 或其他画布，也可在指定工具中制作，但仍使用同一 Token、Logo、尺寸和组件状态。纯图片交付也要提供清晰、完整的页面图，不只给代码。

在新工作目录使用 starter 时，复制后运行 `npm ci` 和 `npm run dev`。不要复制 `node_modules`。在 `src/App.tsx` 或单独页面中组合现有组件；组件 API 以 `src/components/ui/` 的实现为准，别凭名称猜测属性。保留 `src/styles.css` 的明暗主题变量和 `public/brand`，使用真实 Logo 文件，不用重新输入“凹凸时空”代替字标。

让页面体现内容层级和真实业务任务：清楚的标题、主要操作、筛选/状态、主体信息和必要反馈。每个状态使用对应组件；需要新模式时，沿用 Token 与 4px 间距体系扩展，不为单张图另造一套视觉语言。检查输入框与 Select 高度一致、卡片无多余描边、16/24px 图标线性风格、最小正文和操作文字可读。

交付前在目标尺寸打开并目视检查：Logo、对齐、留白、长文本、组件状态、明暗对比、滚动或裁切；若做了暗色版，两版都检查。完成后给用户实际可打开的预览链接或页面图，以及源码位置（若建立或修改了前端），并说明采用了哪些现有组件。已有项目的改版需交代内容与功能核对结果。
